# 数据沙箱收尾与加权多目标调度

本次直接在现有 Spring Boot、原生 JavaScript 和 POI 场景上实现。新增 `WEIGHTED` 调度方式，保留 `BASELINE` 到达顺序调度和 `OPTIMIZED` 单位时间净收益启发式。沙箱通过真实 Java 调度器执行，输入订单由冻结场景和随机种子生成；路线与碳排放仍属于模型估算。

设计参考用户提供的《多目标优化——初识》第12、16、19、21—26页。其中算法与指标示例用于说明加权方法，未直接复制其中把执行时长称为等待时间、使用假定归一化上界等简化口径。

## 一、已经实现的使用流程

1. 打开沙箱，新建或复制实验，设置车辆数、订单数、生成周期、种子及事件。
2. 在“算法”中选择“Weighted · 加权多目标调度”，填写五项相对权重。页面即时显示归一化后的百分比，可恢复默认值。
3. 保存方案或开始实验。Run 冻结配置、权重、场景快照和模型指纹，运行至全部订单运输完成。
4. 查看 Run 的实际订单进度、完成时长与权重摘要。修改方案不会改变历史 Run。
5. 点击“运行同条件基准”，系统以选中 Run 的冻结参数复制独立基准方案，复用同一场景快照；原加权结果保持选中，基准完成后自动加入比较。
6. 导出 Run JSON 或比较 CSV。JSON 包含评分样本；CSV 包含配置、权重、场景和模型标识，以及九项结果指标。

允许权重为0，但五项不能全部为0。后端拒绝负值、非有限数字及超过1000000的权重，前端同时校验。相对权重 `25,25,20,15,15` 与 `.25,.25,.20,.15,.15` 表达相同偏好；保存原始输入，评分时归一化。

## 二、优化模型

每次车辆可派单时，比较若干满足到达时间与容量约束的顺序运输计划。设候选计划为 x，定义：

| 目标 | 数学量 | 方向 | 默认权重 |
| --- | --- | --- | ---: |
| 预测排队等待 | W(x)，本轮开始至取货的排队面积，吨·分钟 | 最小化 | 0.25 |
| 空载里程 | E(x)，车辆至取货点及顺序任务之间的空载公里 | 最小化 | 0.25 |
| 载重里程利用率 | U(x)，载重吨公里除以容量公里，0～1 | 最大化 | 0.20 |
| 本轮运输吨位 | Q(x)，该计划分配的货物吨数 | 最大化 | 0.15 |
| 估算碳排放 | C(x)，车辆油耗与计划里程计算的 kg CO₂ | 最小化 | 0.15 |

默认值是便于启动和展示取舍的主观偏好，没有经过业务标定，也不表示统计求得的最优权重。

### 等待目标

令 q_i 为计划内第 i 个任务的承运吨数，a_i 为从本轮开始到该任务取货的分钟数，R 为当前已到达、尚未分配的总吨数，H 为该候选计划的总执行分钟数，则：

`W(x) = Σ(q_i × a_i) + max(0, R − Σq_i) × H`

第一项统计候选计划内货物等待取货的吨·分钟；第二项把本轮没有服务的已到达货物纳入计划时间窗口，避免只比较已选任务而忽略剩余队列。尚未到达的订单不提前参与派单。已经发生的等待在本轮比较中是共同常数，不重复加入候选目标。

这是单车滚动决策的等待预测，未假定其他空闲车辆在同一窗口内如何服务剩余队列。因此它是调度启发式的局部评价，并非全局排队等待的精确最优化模型。最终结果另按实际取货时间累计货物等待。

### 利用率、吨位与排放

`U(x) = Σ(q_i × d_i_loaded) / [capacity × Σ(d_i_empty + d_i_loaded)]`

其中 capacity 为该车最大载重吨数，d_i_loaded、d_i_empty 分别为任务载重与空载公里。零里程时记为0。本指标同时体现载重程度与里程利用；原页面“车辆利用率”仍保留原口径，即载重公里除以总公里，两者分别展示。

`Q(x) = Σq_i`

全部订单完成时，最终运输吨位通常受固定需求决定。吨位权重表达本轮承运偏好，不能据最终吨位相等判断权重没有生效。

`C(x) = 总行驶公里 × 每百公里油耗 / 100 × 2.68`

2.68 是项目已有的 kg CO₂/L 换算系数。此模型未加入怠速油耗、真实拥堵工况及载重变化对油耗的影响；排放值不代表传感器实测。

### 加权和与无量纲化

先统一为损失向量：

`L(x) = [W(x), E(x), 1−U(x), −Q(x), C(x)]`

对同一次比较的候选集合，记第 j 个损失的最小和最大值为 m_j、M_j：

`z_j(x) = [L_j(x) − m_j] / [M_j − m_j]`

若该目标的候选极差不超过 `1e−12`，则该项统一记0，避免除零。

`α_j = w_j / Σw_j`

`min F(x) = Σ[α_j × z_j(x)]`

w_j 是用户填写的第 j 项相对权重，α_j 是归一化权重，z_j 是无量纲损失，F 是综合损失，越低越优。每组候选用共同的归一化范围；各次派单的范围可能不同，分数不跨轮次或跨 Run 直接比较，也不把动态分数相加宣传为整体改善率。

## 三、求解与约束

对每辆当前可用车辆，先为所有已到达的待分配订单生成单订单候选，避免收益排序提前排除多目标偏好的订单。再加入原收益启发式计划作为备选，从单订单加权排序的前32项进行顺序插入搜索；最多8个任务，并要求该计划累计承运量不超过该车容量。所有候选沿用相同路线、速度、计价及事件模型。

插入时使用当前计划与试插计划的共同范围比较，最终对保留候选重新统一归一化并选择最低分。平分按首个订单的到达时间、订单ID及任务数量确定，输入相同即可复现。选中的任务标记为 `WT`；不会再通过收益优先的回退覆盖加权选择。

这是有搜索上限的滚动启发式，未枚举所有车辆与订单的全局组合，不承诺全局最优、完整 Pareto 前沿或每项指标同时改善。某一权重为0时，相应指标只用于记录，不影响评分。

Run JSON 的 `optimization` 保存方法名、目标顺序、原始与归一化权重、决策次数、候选评估次数，以及前20次决策样本。每条样本含选中订单、目标原值、损失上下界、归一化损失和加权贡献，可手工重算综合分数；超过20次时 `samplesTruncated=true`，明确属于样本而非完整任务轨迹。

## 四、沙箱收尾与兼容

- 权重贯通目录、方案新建、保存、复制、Run 冻结、历史读取、重跑及导出。
- 同条件匹配要求相同场景、模型、种子、车辆、订单、周期和启用事件；算法及目标权重属于策略变量，允许不同。未启用事件的 false 与缺省视为等价。
- 页面区分未完成、失败和完成状态；缺失结果不替换成旧结果，基准为0时改善率保持不可计算。
- 原五项指标保留，新增“货物累计等待（吨·分钟）”和“载重里程利用率（%）”，并保留两项订单完成时长，共九项沙箱结果。
- 表单保存使用打开/切换方案时的版本号，后台轮询不替换表单版本；旧编辑会得到冲突，避免静默覆盖他人修改。
- 开始操作会使先前轮询响应失效；处理动作期间禁止运行历史切换，避免保存中切换目标方案。
- 运行提交遇到网络超时或5xx时保留请求标识，再次点击重试沿用原标识；确认成功或收到明确4xx后才释放标识。
- 模型指纹升级为 `dispatch-20261102-weighted-v1`，全订单结果后缀升级为 `sandbox-all-orders-v3`。旧记录不改写；旧模型不能通过当前代码直接声称精确重跑。
- 24小时历史运行继续按原结束口径识别；开始新实验仍转换为全部订单完成口径。
